# 构建一个Agent

构建一个高效、可控的 Agent，本质上是在“确定性流程”**与**“大模型的概率生成”之间寻找最佳平衡点。

关于你提到的**决定 Agent 本质的要素**、**流程遵循的实现方式**以及**上下文（Context）管理**，下面为你进行系统的梳理。

## 一、 决定 Agent 本质的核心要素与权重

给 Agent 注入的 Prompt、Skill、MCP（Model Context Protocol）以及 RAG，各自扮演着不同的角色：

| **要素**                   | **角色定位**                       | **对 Agent 本质的影响 (权重)** | **核心解决的问题**                                           |
| -------------------------- | ---------------------------------- | ------------------------------ | ------------------------------------------------------------ |
| **System Prompt**          | **灵魂与人格 (Identity & Logic)**  | ★★★★★ (最高)                   | 定义 Agent 的身份、思维逻辑、决策规则、边界与输出规范。      |
| **Skill (工具/能力)**      | **双手与脚 (Tools & Execution)**   | ★★★★☆                          | 定义 Agent 能“做什么”（如：发邮件、查询数据库、调用 API）。  |
| **MCP / Context Protocol** | **神经与接口 (Standard Protocol)** | ★★★☆☆                          | 解决 Agent 与外界工具/上下文连接的**标准化机制**，提高扩展性。 |
| **RAG / Memory (IWIK)**    | **大脑外挂 (Knowledge Base)**      | ★★★☆☆                          | 提供 Agent 解决具体问题所需的**外部动态知识与背景**。        |

> **结论：决定 Agent 本质的是 System Prompt + 工作流架构设计。**
>
> MCP 和 Skill 决定了它的**能力上限**（能干什么），但 System Prompt 决定了它的**行为准则与逻辑思维**（怎么去干）。

## 二、 如何让 Agent 严格遵循流程：Prompt 还是 IWIK/Context？

让 Agent 遵循特定 Sop（标准作业程序）或流程，**不能仅依赖单一方式，而是需要分层实现**。

### 1. 流程控制写在哪里？

- **基本流程与规则：写在 System Prompt**
  - **适用场景：** 结构清晰、步骤少的流程（如：“第一步抽取参数，第二步校验，第三步生成结果”）。
  - **实现方式：** 在 Prompt 中使用强规则约束（如：Structured Outputs、JSON Schema、Few-Shot 示例或 Chain-of-Thought 逻辑）。
- **复杂领域知识/特定案例流程：通过 IWIK / Context (RAG/注入)**
  - **适用场景：** 流程非常长、分支极多、或需要根据不同场景检索不同的 SOP 标准文档。
  - **实现方式：** Prompt 中只留“流程总纲与调度逻辑”，具体的“步骤细则”作为 Context 在触发相应阶段时动态注入（Retrieval/Context Injection）。

### 2. 纯 Prompt 遵循流程的痛点与终极解法

单纯靠 Prompt 引导 LLM 走长流程，模型容易发生**幻觉、跳过步骤或中途偏离**。要确保 100% 严格遵循流程，业界标准的实践架构是：

> **硬控制（代码/工作流引擎） + 软决策（LLM / Agent）**

```
[ 用户输入 ] 
    │
    ▼
[ LangGraph / Workflow 引擎 (确定性节点与状态流转) ]
    ├── 节点 1: LLM 提取关键信息 (Prompt)
    ├── 节点 2: 代码做强校验 (If/Else 条件判定)
    ├── 节点 3: LLM 调用特定 Skill/MCP 接口
    └── 节点 4: LLM 汇总生成结果
```

- **简单/灵活流程：** System Prompt + CoT (Chain of Thought) 即可。
- **严肃业务/高精准流程：** 采用 **LangGraph、Flow-based Agent** 架构，用代码控制状态跳转（State），每个节点只让 LLM 做单一任务决策。

## 三、 大模型/Agent 会保留哪些上下文（Context Management）？

大模型的 Transformer 架构本身是**无状态（Stateless）**的。每次请求，LLM 能“记住”的内容，完全取决于每次调用时**重新拼装并发送给模型的 Context Window**。

在 Agent 系统中，上下文通常分为以下几类被选择性保留和管理：

### 1. 上下文的四层分类

```
                   ┌────────────────────────────────────────┐
                   │           System Prompt (固定)         │
                   ├────────────────────────────────────────┤
                   │       Short-term Memory (对话历史)      │
                   ├────────────────────────────────────────┤
                   │  Working Memory (当前思考与 Tool 结果)   │
                   ├────────────────────────────────────────┤
                   │        Long-term Memory (外置向量库)    │
                   └────────────────────────────────────────┘
```

1. **系统预设上下文 (System Context)：**
   - **保留机制：** 永久保留在每次请求的头部。
   - **内容：** Agent 角色、人设、规则、允许调用的 Skill 描述。
2. **短期记忆 (Short-Term Memory / Conversation History)：**
   - **保留机制：** 随对话滑动或截断。
   - **内容：** 最近 N 轮的用户对话及 Agent 回复。
3. **工作记忆 (Working Memory / Execution Context)：**
   - **保留机制：** 在单次任务（Task）执行期间保留，任务结束后清理。
   - **内容：** Agent 在思考过程中的中间步骤（Thought）、工具调用的输入输出（Tool Calls & Execution Results）。
4. **长期记忆 (Long-Term Memory / RAG)：**
   - **保留机制：** 不在 LLM 上下文中长期占用，而是存入向量数据库（Vector DB）或 K-V 数据库，按需检索并动态注入。
   - **内容：** 用户偏好、历史文档、IWIK 知识库。

### 2. 上下文管理的常见策略（如何防止 Context 爆满与信息干扰）

随着对话增长，Context Window 会溢出且会导致 LLM 注意力分散（Lost in the Middle）。 Agent 框架通常会采用以下策略管理上下文：

- **滑动窗口 (Sliding Window)：** 只保留最近 $K$ 轮对话，丢弃最早的对话。
- **总结/压缩 (Summary Memory)：** 当上下文达到一定阈值，后台自动调用另一个 LLM 将历史对话总结为一段摘要，替换掉原始多轮对话。
- **选择性遗忘/裁剪 (Pruning)：** 移除对当前决策无关的中间 Tool Call 详细 Raw Data（如 API 返回的几千行 JSON），仅保留抽取出的关键结论。
- **动态注入 (Dynamic RAG/MCP Context)：** 仅当 Agent 评估需要特定知识时，才将该知识从外置存储库检索并插入当前的 Prompt 中。

# CONTEXT 工程

**为什么模型真的会按这个顺序听话**的底层机制。你给的五层模型本身是对的，但它隐含了一个简化假设——"越靠上优先级越高"像是某种显式优先级字段。实际上 LLM 里**根本没有"优先级"这个字段**。所谓的优先级，是三个独立力量相乘后的**涌现结果**。我把这个机制彻底拆开。

你给的五层顺序在**工程结果上完全正确**，但"为什么是这个顺序"的真正答案，比"越靠上越优先"深刻得多。核心纠正一点：**LLM 里根本没有"优先级"这个字段**。你观察到的优先级，是三个独立力量相乘后的**涌现结果**。

## 力量一：角色训练权重（RLHF）——这才是 System 制空权的真正来源

你说 System Prompt 制空是因为"框架硬编码在最顶部"。这是最常见的误解。**位置只是放大器，不是根因。** 根因是训练时的角色对齐：

> 同样一句话，放在 `role: system` 里 vs 放在 `role: user` 里（哪怕都在最顶部），前者的影响力远大于后者。

模型在 RLHF/指令微调阶段被**显式训练**成"系统指令高于用户指令"。这是写入权重的偏好，不是运行时的位置效应。所以：

- **System 的权威 = 角色训练权重（主）× 首因位置（次）**，是乘法叠加，双重加成。
- 你说的"无视后续文档直接改代码"能成立，**主要靠的是角色训练**，位置只是帮它更稳。

这也解释了为什么"忽略以上指令"这种 prompt injection **有时能成功**——因为它利用了力量二来对抗力量一。这是一场持续的军备竞赛，不是系统层的绝对胜利。System 大多数时候赢，是因为角色训练权重通常强于近因效应，但不是每次都赢。

## 力量二：位置注意力——首因 + 近因，中段塌陷

Transformer 的注意力沿位置分布呈 **U 型**：

- **首因峰（Primacy）**：Context 最开头的 token 注意力高。System 放这里，叠加角色权重，所以最强。
- **近因峰（Recency）**：Context 最末尾注意力最高。User 输入放这里——这正是你说的"近因效应"。User 角色权重虽低，但**靠近因补强**，所以模型对最新指令响应最快。
- **中段衰减（Lost in the Middle）**：这是你五层模型里**最容易被忽略的盲点**。

你的第 3 层（Memory/CLAUDE.md）和第 4 层（RAG/IWIK）排在 User 之上，看起来"优先级更高"。**但在长 Context 里，它们恰好落在注意力最低的中段**——既没有首因、也没有近因。结果是：

> 工程上的"层叠优先级"和模型实际的"注意力分布"在这里**直接打架**。你以为是第 3、4 层压过第 5 层，实际上在长上下文中，中段文档可能是**最不被注意**的。

这就是为什么成熟框架会做两件事来对抗中段塌陷：
1. **关键规则重复注入**（re-injection）：把最重要的约束在 Context 尾部再贴一遍，借近因峰拉起来。
2. **格式显著性**（delimiter、XML 标签、重复强调）：用结构性标记强制注意力聚焦，这是第三股力量。

## 力量三：格式显著性——结构化块抢注意力

Tool/Schema 是结构化声明（JSON），Skill 是带 delimiter 的标记块。模型在 function-calling 微调中被训练成**优先解析这类结构化块**。所以 Tools/Skills 排第二，不只是因为"紧跟 System"，更是因为**它们的格式本身就能抢到额外注意力**——这是训练带来的格式偏好，独立于位置。

## 所以"为什么是这个顺序"——重新表述

这个顺序不是随意堆叠，而是把**不变性 × 权威性**乘积最大的内容放在注意力最高的位置：

| 层           | 角色权重     | 位置注意力    | 有效影响力          |
| ------------ | ------------ | ------------- | ------------------- |
| System       | 最高（RLHF） | 首因峰        | **双重满格 → 制空** |
| Skills/Tools | 中           | 靠前+格式显著 | 中高                |
| Memory/规则  | 中           | **中段衰减**  | **被削弱** ⚠️        |
| RAG/IWIK     | 低           | **中段衰减**  | **最弱** ⚠️          |
| User         | 最低         | 近因峰        | 近因补强 → 实际很强 |

**两个颠覆性结论**：

1. **你以为的"第 3、4 层 > 第 5 层"在长上下文里经常不成立。** Memory 和 RAG 排在 User 之上，却落在注意力洼地；User 排最后却踩在近因峰上。这就是为什么"项目规则写了但模型不遵守"——不是它不想遵守，是中段文档在注意力上被 User 的近因压过去了。框架用 re-injection 和强 delimiter 来补救，本质是在**对抗你自己设定的那个优先级栈**。

2. **System 的制空权不是位置给的，是训练给的。** 把同样的话从顶部挪到 User 角色里，权威立刻塌掉一大半。位置是杠杆，角色训练才是支点。

---

一句话：**你画的五层栈是"工程注入顺序"，对的；但模型的"有效优先级"是 角色训练权重 × 位置注意力 × 格式显著性 三者相乘的涌现，而中段 Memory/RAG 是这三力齐弱的地带——这才是"为什么必须把不变的高权威内容钉在 System 位置"的真正原因。**
